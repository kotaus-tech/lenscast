# Протокол Lenscast 1

Все числа — big-endian. TCP_NODELAY на обоих концах. Один активный ПК.
Телефон — сервер; ПК — клиент. Звук и текстовый ввод отсутствуют.

## Управление (реализовано в блоке А)

Wi-Fi: TCP 27183, TLS 1.2 или 1.3, сертификат AndroidKeyStore.
USB: TCP 27185, **только 127.0.0.1**, доступ через `adb forward tcp:27185 tcp:27185`.
Никогда не переключать Wi-Fi на незашифрованный порт при ошибке TLS.

Сообщение: `uint32 размер` + UTF-8 JSON, размер 2…65536 байт. После
недопустимой длины, обрыва или тайм-аута внутри сообщения соединение закрывается.
JSON выбран для небольшого канала управления; бинарное кадрирование позволяет
менять команды без синхронного изменения всех структур. Неизвестные команды игнорируются.

Первое сообщение ПК:
`{"type":"hello","version":1,"code":"123456","token":""}`.
При повторном подключении `code` пуст, передаётся `token`.
USB игнорирует оба поля. Несовместимая версия отклоняется.

Первый TLS-сеанс: сертификат ещё не доверенный; пользователь подтверждает телефон
кодом из его интерфейса. После успешной проверки ПК сохраняет SHA-256 сертификата
и 256-битный случайный токен под DPAPI CurrentUser. Последующие сеансы требуют
точного совпадения отпечатка, иначе автоматическое соединение прекращается.
При смене DHCP-адреса ПК узнаёт ранее сопряжённый телефон по отпечатку сертификата.
Подмена сертификата на известном IP не принимается.
Телефон хранит только SHA-256 токена в закрытом хранилище приложения.
Это доверие при первом подключении, не PAKE: первое сопряжение выполняется только
в доверенной домашней сети. Код живёт 3 минуты, меняется при выдаче токена и после
5 ошибок; после 5 ошибок пауза 30 секунд. Токены и коды не журналируются.

Ответ: `ready {version,name,mode,token?,videoTicket}`, `pairing {message}` или `error {message}`.
Токен выдаётся только после правильного кода и принятия активного соединения.
Команды ПК: `ping {sent}`, `stop`, `forget`, `keyframe`, `videoCodec {codec:1|2}`,
`navigation {action:back|home|recents}`, `touch {action:down|move|up|cancel,x,y}`.
Координаты нормированы 0…1 относительно изображения без чёрных полей. Одна
продолжаемая точка касания; move объединяются, up/cancel не теряются. ПК обновляет
удержание каждые 250 мс; телефон завершает его при отсутствии ввода более 1,5 с,
потере управления или смене геометрии. `notice {message}` — действие для пользователя.
`sent` — монотонные микросекунды ПК, вычисленные из Stopwatch.
Ответ `pong {sent,phoneUs}`: phoneUs — elapsedRealtimeNanos / 1000.
`forget` удаляет доверие на телефоне; ПК удаляет локальное сопряжение выбранного телефона, не затрагивая второе.
При потере связи ПК повторяет подключение с паузой 1,5 с после первого успешного
сеанса. Тайм-аут отсутствия сообщений — 6 с. Захват в последующих блоках не должен
зависеть от этих переподключений.

`telemetry` раз в секунду: `battery` (%, -1 если неизвестно), `charging` (bool),
`temperature` (°C аккумулятора, **не датчик процессора**), `thermal` (Android thermal
status), `network`, `rssi` (dBm), `fps`, `bitrate` (бит/с), `dropped`.
В блоке B fps/bitrate измеряются по выходу кодировщика, dropped — сбросы
очереди телефона; если экран не передаётся — fps/bitrate = 0; в интерфейсе не выдаются за измерение потока.

## Видео (реализация блока B, аппаратная проверка отдельно)

Отдельный сокет: TLS 27184 / USB loopback 27186. Аутентификация случайным 256-битным `videoTicket` текущего
сеанса управления перед отправкой кадров; TLS-отпечаток тот же. Не смешивать
соединения разных сессий. Заголовок 24 байта:
`magic uint32 = 0x4C435631`, `version uint8 = 1`, `type uint8` (0 config, 1 delta,
2 key), `codec uint8` (1 AVC, 2 HEVC), `flags uint8` (зарезервировано),
`timestampUs uint64` (монотонные часы телефона), `size uint32` (1…16777216),
`sequence uint32`. Затем пакет Annex B; config начинается с `uint32 width, uint32 height`, затем SPS/PPS (+VPS для HEVC).
Первое сообщение видеосокета: такое же BE32/JSON кадрирование, как управление,
`{version:1,ticket:videoTicket}`. Нет кода сопряжения/постоянного токена в видеоканале.
Билет выдаётся только после принятия управляющего сеанса, привязан также к
транспорту и отзывается при его разрыве. Старый билет не принимается. TLS-пин
второго сокета строго совпадает с проверенным сертификатом первого.

H.264 обязателен. HEVC запрашивается ПК только после проверки доступного Microsoft
Media Foundation MFT с NV12. Телефон выбирает аппаратный HEVC только по реальным
CodecCapabilities; иначе AVC. При отказе HEVC на ПК — возврат к AVC. Профили,
размеры и 30 FPS проверяются по VideoCapabilities, неподдерживаемые не обещаются.
Захват MediaProjection переживает сетевое переподключение, но не отзыв согласия
Android. При повороте меняются encoder Surface/VirtualDisplay.resize без второго
createVirtualDisplay на том же токене. Сервер/ПК имеют очереди по три пакета;
при потере зависимости — config + ожидание IDR. Кодировщик не ждёт сокет.

Метки Surface/MediaCodec переводятся из System.nanoTime в elapsedRealtimeNanos
для согласования с pong.phoneUs. Сквозная задержка до физического дисплея в блоке B
не измерена и в интерфейсе не выдаётся за RTT.

Очередь декодера ограничивается, после переполнения пропуск до ключевого кадра
и запрос IDR. Синхронизация часов: серия ping/pong, смещение по середине RTT,
выбор минимального RTT. Задержка кадра = часы ПК − скорректированная метка телефона.
В блоке А задержка **не измеряется**: видеокадров пока нет.


В текущем блоке синхронизация по минимальному RTT уже реализована; в интерфейсе
показывается только «отклик связи», то есть RTT управления. Телефон закрывает
активный сеанс без команд ПК более 8 с. Это не измерение сквозной видеозадержки.

## C · камера (0.3.0)

`ready.mode` равен «Веб-камера»: тот же control-scoped videoTicket и LCV1-канал;
трансляция экрана и камера не работают одновременно. Видео камеры кодируется в
sensor-native размерах, configuration/CSD и IDR приходят заново после смены сессии.
Временная метка — monotonic time получения закодированного кадра на телефоне,
не raw SENSOR_TIMESTAMP и не измеренная сквозная задержка.

`telemetry.camera`: `running`, `ready`, русский `status`, `cameraId`, `mode`,
`rotation` (0/90/180/270), `mirror`, `actualFps`, `actualIso`, `actualExposureMs`,
`codec`; `cameras[{id,label}]`; `modes[{id,width,height,low,high}]`;
`controls[{key,label,value?, min?,max?,step?,values?,boolean?}]`.
Модули перечисляются только среди прямо открываемых ID с совместимыми metadata
режимами AVC. Список `modes` — кандидаты Camera2 + VideoCapabilities (не более 200),
не обещание успешной сессии/OEM FPS. `ready=true` требует настоящих capture callback
и encoded keyframe; actualFps измерен. Metadata старой камеры при остановке может
оставаться, но `running=false` запрещает действия UI. Структура ограничена framing
64 КиБ; подписи не содержат pairing codes/tokens или содержимого экрана.

Команда `cameraSet`: необязательные `cameraId`, `mode` из текущих списков,
`rotation`, `mirror`, `reset:true`, `controls:{key:value}`. Модуль/reset инициируют
полную пересборку со своими настройками; параметры разных модулей в одной команде
не смешиваются. Ключи controls: `zoom`, `focusMode` (CameraMetadata AF enum),
`focus` (диоптрии, применяется при AF OFF), `ev` (целый шаг EV), `aeLock`,
`awbMode` (AWB enum), `awbLock`, `torch`, `videoStabilization`,
`opticalStabilization`, `manualExposure`, `iso` (целое), `exposureMs`.
Доступны только объявленные ключи; сервер проверяет тип/диапазон/request keys.
Одновременный EIS и OIS отклоняется. Manual exposure ограничена периодом
выбранного FPS; при auto ISO/выдержка остаются у HAL. Успешно принятые настройки
сохраняются в приватных prefs телефона, отдельный профиль на cameraId.

Поворот/отражение — metadata для preview (и будущего D), не изменение Annex B.
Камера стартует только локально из видимого Activity после CAMERA permission;
команда ПК не может открыть камеру в фоне. Разрыв управления отзывает video ticket,
но не останавливает явно запущенную пользователем camera FGS. «Стоп» связи закрывает
и camera, и screen FGS. Watchdog кадров камеры — 10 с, после него локальный повторный
старт/чёрный OEM-fallback, не попытка обхода privacy.


0.3.1: camera telemetry дополнительно содержит `generation` и
`proof:{capture,config,key,frames}` для точной диагностики текущей сессии.
`ready=true` требует все три независимых подтверждения, в любом порядке.
При reset/смене сессии старые proof не используются; тест проверяет новый CSD/IDR
также на реальном видеосокете. Это не диагностический экран и не запись изображения.
